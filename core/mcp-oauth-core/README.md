# MCP OAuth core

Java 17, no third-party dependencies. This module supplies client-registration policy, Client ID Metadata Document (CIMD) validation, callback validation, and a reusable authorization-code/PKCE and refresh engine. Host adapters perform HTTP I/O, JSON decoding, browser interaction, callback hosting, and credential storage.

Run `./gradlew :mcp-oauth-core:build` from the repository root to produce `core/mcp-oauth-core/build/libs/mcp-oauth-core-0.1.0.jar` and its sources JAR and run the registration fixtures and an external-package consumer. The exported package is `com.mcpscanner.core.oauth`.

`OAuthChallengeParser` follows RFC 9110 §11.6.1. A field may repeat the `Bearer` challenge, and the parameters merge. A repeated parameter name is rejected as ambiguous (`INVALID_CHALLENGE`).

## Registration selection

Call `new RegistrationSelector().select(request)` with a `RegistrationRequest` containing the discovered issuer, optional issuer-bound `RegisteredClient`, optional CIMD URL, `AuthorizationServerCapabilities`, actual callback URI, and `RegistrationMode`.

Auto selects configured credentials, then configured CIMD when advertised, then an advertised DCR endpoint. Missing options raise `RegistrationException` with `MISSING_REGISTRATION`; unavailable explicit modes raise `UNSUPPORTED_MODE`. Invalid selected configuration raises its specific typed reason and never triggers another registration mechanism. Pre-registered issuer matching uses exact strings. CIMD selection returns its URL as `clientId`, without a secret. DCR selection returns its registration endpoint for the host adapter to call.

## CIMD validation

`CimdDocumentValidator.validateLocation(location, callback)` checks the configured URL and callback before selection. Metadata URLs require HTTPS, a host and path, and no user information or fragment. The callback must be a fixed nonzero-port HTTP callback at the IP loopback address `127.0.0.1` or `::1`.

After bounded HTTP retrieval and JSON parsing, call `validate(location, document, callback)`. The document must contain an exact URL `client_id`, a nonblank `client_name`, a string array `redirect_uris` containing the exact callback, and an absent or `none` `token_endpoint_auth_method`.

The host remains responsible for safe HTTP fetching, discovery and endpoint validation, redirect policy, token security, and showing typed failures to the user. Registered credentials and selections omit client secrets from their `toString()` output.

## Authorization callback validation

Call `AuthorizationCallbackValidator.validate(expectedState, expectedIssuer, issuerParameterSupported, callback)` before displaying callback errors or exchanging authorization codes. The immutable `AuthorizationCallback` carries the received state, issuer, code, error, and error description; the validator returns it only after the checks pass.

State must match exactly. When validated authorization-server metadata advertises `authorization_response_iss_parameter_supported=true`, an issuer parameter is required. Otherwise it may be absent, but every present issuer must exactly equal the expected issuer string without URL normalization. Rejected callbacks raise `CallbackValidationException` with `STATE_MISMATCH`, `MISSING_ISSUER`, or `ISSUER_MISMATCH`; these messages never include callback error descriptions. The same rules apply to successful and error callbacks.

## Authorization-code and refresh flow

Construct `OAuthFlowEngine(TokenExchange, BrowserAuthorization, CredentialStore, Clock)` and call `authenticate(AuthorizationCodeConfig)` or `refresh(config)`. The config supplies validated issuer/resource metadata, an issuer-bound registered client, authorization/token endpoints, the actual registered callback URI, scopes, and the callback issuer-advertisement flag. Registration selection and CIMD/DCR network operations occur before this flow; pass the resulting client to the config. CIMD remains configurable and does not assume any production hosted document URL.

`TokenExchange` receives a complete `TokenRequest`: POST method, endpoint, headers, form parameters, and the encoded form body. It returns `TokenResponse(status, genericJsonFields)`. The adapter must use that request unchanged, enforce bounded responses/timeouts and safe redirect/TLS policy, and perform only generic JSON decoding. It must not interpret token fields or construct grant parameters. The engine owns those rules. Public clients and `client_secret_post` clients send `client_id` in the form; `client_secret_basic` clients identify themselves only in the `Authorization` header, because some servers (Better Auth 1.6.10) treat a form `client_id` as `client_secret_post` and reject the request. Other token-endpoint authentication methods are not supported.

`BrowserAuthorization` receives `AuthorizationRequest` with encoded `uri()` and parameters; it returns `BrowserCallback` containing the matched callback location and parsed `AuthorizationCallback` parameters. The engine generates fresh secure state and S256 proof, validates the exact callback location, state and advertised issuer, then exchanges the code. Browser/callback timeouts and cancellation belong to the adapter.

`CredentialStore` loads/saves by `CredentialBinding` (exact issuer, exact protected-resource URI, client ID, and requested scope set). `OAuthCredential` retains granted scopes, access/refresh token and an optional expiration instant; `expiresAt == null` means the token endpoint omitted expiry. The store must replace each credential atomically; consumers must serialize flows for a binding so rotating refresh tokens cannot race across engines or processes. Invalid responses never replace stored credentials. Refresh preserves the previous refresh token when the response omits one, and persists a rotated token when present.

`OAuthTokenRefreshPolicy` owns the 30-second expiry decision and the three-consecutive-failure terminal state. Use `WAIT_FOR_CHALLENGE` for an authorization-code credential whose server omitted expiry; use the default `REFRESH` behavior when a fresh grant can be acquired without a refresh token. The host performs the actual refresh and serializes decision, exchange, and outcome recording for each credential.

The engine accepts HTTPS endpoints and HTTP loopback fixture/callback endpoints, rejects user information/fragments and invalid scope tokens, and validates token type, bearer-safe token contents, scopes, status and expiry. All request, response, callback, credential and config diagnostic representations redact sensitive values. Adapter exceptions are converted to fixed-message typed failures without retaining their potentially sensitive causes.

## Discovery and authorization challenges

`OAuthChallengeParser.parse(List<String>)` handles all `WWW-Authenticate` header values, other authentication schemes, escaped quoted values and quoted commas. It returns an optional `BearerChallenge`. Duplicate Bearer challenges or parameters, invalid scope tokens, malformed values and unsafe metadata locations raise a fixed-message `OAuthPolicyException`. Server `error_description` is discarded. Challenge and decision diagnostic strings are redacted.

`OAuthDiscoveryPolicy.protectedResourceLocations(resource, challenge)` prefers the challenge's `resource_metadata`; otherwise it returns path-specific and root protected-resource well-known candidates in order. `authorizationServerLocations(issuer)` returns RFC 8414 and both OIDC path variants in order. `validateResourceMetadata(requestedEndpoint, jsonFields)` accepts an exact or same-origin ancestor resource and returns `ProtectedResourceMetadata` with the original advertised OAuth audience; cross-origin and sibling paths fail. `validateIssuerMetadata(expectedIssuer, jsonFields)` requires an exact issuer string match. The requested endpoint must be independently selected; never replace it with an unvalidated response value. Metadata fetches, bounded decoding, redirects, network destination policy, authorization-server selection and issuer trust approval remain host responsibilities. The core permits HTTPS and IP-loopback HTTP fixtures.

`initialScopes(challenge, metadata.scopes())` uses challenge scopes when present, including scopes absent from metadata; otherwise it uses protected-resource scopes. An empty set means omit the scope parameter.

Start `OAuthRetryState.start(binding, operation)` for each original operation. Pass it with the HTTP status, parsed challenge, current binding, token/refresh availability and `AuthorizationApproval` into `OAuthChallengePolicy.decide(...)`. A 401 can request one refresh and then an approved authorization. Only a 403 Bearer `insufficient_scope` challenge can request a scope upgrade. Requested scopes accumulate by union. The caller first uses `REQUIRE_PROMPT`, then supplies `APPROVED` or `DENIED` for that exact proposed scope set. Denial is terminal; no authorization occurs while approval is pending. `AUTHORIZE` is a generic instruction to invoke the explicitly configured grant; this policy never selects a grant from a status code.

Retain each decision's `nextState()` while retrying the same resource/operation. States are immutable, bind issuer/resource/client identity, stop repeated failing scope sets, and cap combined refresh/authorization retries at two by default (constructor range 1–3). Hosts serialize operation recovery, retain retry state across challenge rounds, enforce approval for the actual scope set, and replay only operations that their transport adapter considers safe. Start a fresh state for a fresh user operation. No HTTP, browser or token side effects occur inside these policy classes.

The behavior follows the published [2026-07-28 authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) and [discovery requirements](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery), checked 2026-10-20. The initial scope and discovery fallbacks also apply to the [2025-11-25 specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization). Grant extensions retain their own explicit version and stability policy.

## Optional Client Credentials grant (draft)

`ClientCredentialsFlow` implements the optional [MCP OAuth Client Credentials extension draft](https://github.com/modelcontextprotocol/ext-auth/blob/main/specification/draft/oauth-client-credentials.mdx), checked 2026-10-20. A host explicitly selects this grant for a pre-registered confidential client. A 401 never chooses it automatically. The flow has no browser, CIMD or DCR fallback.

Build `ClientCredentialsConfig` from an independently selected `CredentialBinding`, validated `ProtectedResourceMetadata`, `ClientCredentialsMetadata`, issuer-bound `RegisteredClient`, and `ClientCredentialsAuthentication`. The selected issuer must exactly match both registration and authorization-server metadata and appear in the protected-resource issuer list. The protected-resource identity must match exactly. Metadata must explicitly advertise the `client_credentials` grant and selected token authentication method. The shared HTTPS/IP-loopback location and scope policies apply; host network, metadata trust and bounded I/O policies remain mandatory.

Use `ClientCredentialsAuthentication.basic()` for advertised `client_secret_basic`; the secret is transmitted exclusively in RFC 6749 Basic authentication with each component form-encoded. The draft's metadata names Basic while its prose/example shows a form-body secret. This implementation follows the advertised method and does not silently substitute `client_secret_post`.

Use `privateKeyJwt(algorithm, optionalKeyId, signer)` for advertised `private_key_jwt`. The selected asymmetric algorithm must also be advertised in `signingAlgorithms`. Supported JOSE names are RS256/384/512, PS256/384/512, ES256/384/512 and EdDSA; symmetric and unsigned assertions are rejected. `ClientAssertionSigner.sign(algorithm, signingInput)` receives the exact ASCII JWS signing input and returns its raw JOSE signature bytes. The adapter owns private-key access and must apply the requested algorithm correctly, including JOSE ECDSA signature encoding. The core never receives private keys. It constructs and JSON-escapes the JWT header and claims: client ID as both `iss` and `sub`, exact token endpoint as `aud`, injected-clock `iat`, a 60-second `exp`, and fresh random `jti`. It rejects null/empty/oversized signatures and sanitizes signer failures. The trusted signer port guarantees cryptographic signing; the external consumer fixture verifies a real RSA signature at a local token endpoint. JWT requests omit `client_id` because the assertion identifies the client.

Construct `ClientCredentialsFlow(TokenExchange, CredentialStore, Clock)`. `authenticate(config)` always performs a new machine grant. `credential(config)` uses an exactly bound, sufficiently scoped stored credential until 30 seconds before expiration, then performs another machine grant. Missing expiration causes reacquisition on the next call. Returned refresh tokens are discarded; renewal always sends `grant_type=client_credentials`. Invalid or denied responses never replace a stored credential. Methods serialize calls within one flow instance; hosts must serialize across instances/processes sharing a store. Failures use fixed-message `OAuthFlowException` values without adapter causes or response descriptions.

`CredentialBinding` includes `OAuthGrantMode` in identity and hash codes. The existing four-argument constructor remains available and defaults to `AUTHORIZATION_CODE`; machine grants require the five-argument constructor with `CLIENT_CREDENTIALS`. Persistent adapters must include the grant mode in storage keys, with old records interpreted as authorization-code grants. Retry states reject a grant-mode change. The module's tests cover the external consumer, binding/authentication/expiry/denial fixtures, signer failure fixtures, and a real loopback token endpoint validating an RSA client assertion.

## Optional Enterprise-Managed Authorization (stable)

`EnterpriseManagedFlow` implements the [stable MCP Enterprise-Managed Authorization profile](https://github.com/modelcontextprotocol/ext-auth/blob/main/specification/stable/enterprise-managed-authorization.mdx), checked 2026-10-20. Select this mode explicitly with `OAuthGrantMode.ENTERPRISE_MANAGED`. A 401 never selects it or enables enterprise SSO. Configuration must contain validated protected-resource metadata, resource authorization-server metadata, an exactly issuer-bound registered client, and an explicit `EnterpriseIdentityProvider` adapter. No hosted CIMD URL is assumed; a supplied hosted document URL can be the public client ID after registration selection.

Prerequisites: the enterprise must configure client sign-in/registration at its IdP, permit the requested MCP resource and scopes by policy, and establish IdP trust at the resource authorization server. The resource authorization server must advertise `urn:ietf:params:oauth:grant-profile:id-jag` in `authorization_grant_profiles_supported`. Populate `EnterpriseAuthorizationMetadata.grantProfiles` from that field, plus issuer, token endpoint, token authentication methods and signing algorithms. Issuer, resource, client ID, scope set and grant mode are validated before either loading a cached token or contacting the IdP. The configured issuer must be advertised by the exact protected resource.

Construct `EnterpriseManagedFlow(EnterpriseIdentityProvider, TokenExchange, CredentialStore, Clock)`. The shared flow constructs the RFC 8693 request with the token-exchange grant, requested ID-JAG type, exact resource authorization-server issuer as `audience`, and requested scopes. `EnterpriseManagedConfig.includeResource` controls the profile's optional `resource` parameter; when included its value is always the exact protected-resource identifier. `EnterpriseIdentityProvider.exchange(EnterpriseIdentityRequest)` supplies an already configured enterprise sign-in identity, adds its subject token and subject-token type and required IdP client authentication, and sends the request to its configured IdP. It must preserve the core-built parameters and return generic `TokenResponse` fields. The adapter owns IdP-specific OIDC/SAML sign-in, optional SAML-to-refresh-token conversion, enterprise tenant/user isolation and IdP credential renewal. This port does not imply universal enterprise SSO support.

The core rejects IdP denial, wrong `issued_token_type`, wrong `N_A` token type, invalid assertion text, nonpositive advertised expiration and reduced returned scopes before contacting the resource authorization server. It then constructs the RFC 7523 JWT-bearer grant with the ID-JAG as `assertion`. `TokenExchange` sends that complete request unchanged under the same bounded I/O/TLS/redirect policy as other shared flows. SSO subject tokens and IdP client credentials stay at the IdP; they must never be forwarded to the resource authorization server. ID-JAG signature/issuer/audience/resource/client policy verification is the resource authorization server's responsibility; the client does not infer claims or authorization from an opaque assertion.

Resource authorization-server authentication shares the machine-grant request builder and signer policy: advertised `client_secret_basic`, advertised `private_key_jwt` with an advertised asymmetric algorithm and injected signer, or explicitly advertised `none` via `ClientCredentialsAuthentication.publicClient()`. A public client with a configured secret is rejected. The JWT authorization grant's `assertion` and a private-key client's `client_assertion` remain distinct. The existing machine grant remains confidential-only.

`authenticate(config)` always performs both exchanges. `credential(config)` reuses only an exactly bound, sufficiently scoped token with more than 30 seconds remaining, then repeats both exchanges at expiration; absent expiration also causes renewal. Resource-server refresh tokens are discarded; enterprise renewal obtains a new ID-JAG rather than silently switching grants. A denied/invalid exchange never replaces a stored token. Each flow instance serializes calls; hosts must serialize across instances/processes and isolate enterprise users/tenants in their credential-store adapter. Exceptions and diagnostic representations redact assertions, credentials and remote error descriptions. The module's tests cover the external consumer and enterprise two-hop, public/Basic/JWT, denial, malformed response, exact binding, optional-resource, renewal and sanitized-failure fixtures.
